## CPU에게 여러 개씩 먹여보기



<p>스태프 핫도그 #8에서 이런 이야기를 했습니다.</p>

<blockquote>
<p>CPU는 생각보다 놀고 있다.</p>
</blockquote>

<p>오늘은 그 말을 직접 확인합니다. 설명만 듣지 않아요. 코드를 봅니다. 어셈블리를 봅니다. 벤치마크도 봅니다. 그리고 마지막에는 이런 감각을 가져갑니다.</p>

<blockquote>
<p>나는 하나씩 계산한다고 썼다. CPU는 여러 개씩 계산하고 있었다.</p>
</blockquote>



## 오늘의 메뉴



<p>오늘 만들 것은 <strong>내적</strong>입니다. 영어로는 dot product.</p>

<p>두 벡터가 있어요.</p>

<pre><code>a = [1, 2, 3, 4]
b = [5, 6, 7, 8]</code></pre>

<p>내적은 이렇게 계산합니다.</p>

<pre><code>1*5 + 2*6 + 3*7 + 4*8 = 70</code></pre>

<p>코드로 쓰면 더 단순해요.</p>

<pre><code>sum += a[i] * b[i];</code></pre>

<p>이 한 줄. 곱하고. 더한다. 끝.</p>

<p>그런데 이 한 줄은 생각보다 많은 곳에 있습니다.</p>

<ul>
<li>벡터 검색</li>
<li>추천 시스템</li>
<li>머신러닝</li>
<li>행렬 곱셈</li>
<li>신호 처리</li>
<li>이미지 처리</li>
</ul>

<p>AI 시대에 CPU와 GPU가 열심히 하는 일도 결국 이 모양을 많이 닮았어요. 곱하고 더한다. 곱하고 더한다. 그래서 오늘의 메뉴는 내적입니다.</p>



## 준비물



<p>M 시리즈 맥북 기준으로 설명합니다. M1, M2, M3, M4 모두 큰 흐름은 같아요.</p>

<p>컴파일러는 <code>clang</code>. 먼저 확인합니다.</p>

<pre><code>clang --version</code></pre>

<p>어셈블리는 <code>-S</code> 옵션으로 봅니다.</p>

<pre><code>clang -O3 -S dot.c -o dot.s</code></pre>

<p>벤치마크도 같이 돌립니다. 숫자는 환경마다 다릅니다. 오늘 중요한 것은 숫자 하나가 아니에요. 중요한 것은 <strong>방향</strong>이다. 그리고 어셈블리에 남는 <strong>흔적</strong>이다.</p>

---



## 1단계 — 가장 단순한 내적 코드



<p>파일 이름은 <code>dot.c</code>.</p>

<pre><code>#include &lt;stddef.h&gt;

float dot(
    const float *a,
    const float *b,
    size_t n
) {
    float sum = 0.0f;

    for (size_t i = 0; i &lt; n; i++) {
        sum += a[i] * b[i];
    }

    return sum;
}</code></pre>

<p>이 코드는 하나씩 계산하는 것처럼 보여요.</p>

<pre><code>sum += a[0] * b[0]
sum += a[1] * b[1]
sum += a[2] * b[2]
sum += a[3] * b[3]
...</code></pre>

<p>앞에서부터 하나씩. 차례대로. 하지만 컴파일러는 이 코드를 다르게 볼 수 있습니다. 컴파일러는 묻습니다.</p>

<blockquote>
<p>이 계산을 꼭 이 순서대로 해야 하나?</p>
</blockquote>

<p>내적의 각 곱셈은 서로 <strong>독립</strong>이에요.</p>

<pre><code>a[0] * b[0]
a[1] * b[1]
a[2] * b[2]
a[3] * b[3]</code></pre>

<p>먼저 무엇을 곱해도 됩니다. 동시에 곱해도 됩니다. 마지막에 합치면 돼요. 이게 SIMD가 좋아하는 모양입니다.</p>



## 2단계 — 컴파일해서 어셈블리 보기



<p>먼저 최적화 없이 컴파일합니다.</p>

<pre><code>clang -O0 -S dot.c -o dot_o0.s</code></pre>

<p>그리고 최적화를 켜고 컴파일합니다.</p>

<pre><code>clang -O3 -S dot.c -o dot_o3.s</code></pre>

<p>두 파일을 비교해보세요. <code>-O0</code>는 C 코드를 거의 있는 그대로 옮기려 합니다. <code>-O3</code>는 컴파일러가 적극적으로 바꿉니다.</p>

<p>우리가 찾고 싶은 것은 이런 모양이에요.</p>

<pre><code>fmul
fadd</code></pre>

<p>또는 더 반가운 모양.</p>

<pre><code>fmla</code></pre>

<p>ARM에서 <code>fmla</code>는 fused multiply-add 계열 명령입니다. 곱하고 더한다. 내적의 핵심이에요.</p>

<p>그리고 더 중요한 것은 <strong>레지스터 표기</strong>입니다.</p>

<pre><code>v0.4s</code></pre>

<p>여기서 <code>v0</code>는 벡터 레지스터예요. <code>.4s</code>는 그 안을 32-bit float 4개로 보겠다는 뜻입니다.</p>

<pre><code>v0.4s = [float, float, float, float]</code></pre>

<p>M 시리즈의 NEON 벡터는 128-bit. float 하나는 32-bit. 한 벡터에 float 4개가 들어갑니다.</p>

<pre><code>128 bit = 32 bit × 4</code></pre>

<p>그러니까 이런 명령이 보인다면,</p>

<pre><code>fmul v0.4s, v1.4s, v2.4s</code></pre>

<p>의미는 이겁니다.</p>

<pre><code>v0[0] = v1[0] * v2[0]
v0[1] = v1[1] * v2[1]
v0[2] = v1[2] * v2[2]
v0[3] = v1[3] * v2[3]</code></pre>

<p>명령어 하나. float 곱셈 네 개. <strong>이게 SIMD입니다.</strong></p>



## 3단계 — 중요한 한 줄



<p>우리는 이렇게 썼어요.</p>

<pre><code>sum += a[i] * b[i];</code></pre>

<p>하지만 CPU는 이런 식으로 처리할 수 있습니다.</p>

<pre><code>[a0, a1, a2, a3]  ×  [b0, b1, b2, b3]
=  [a0*b0, a1*b1, a2*b2, a3*b3]</code></pre>

<p>부분합들을 나중에 합치면 돼요. 즉 CPU는 이렇게 생각합니다.</p>

<pre><code>하나씩 곱하지 말고, 네 개씩 곱하자.
하나씩 더하지 말고, 묶어서 더하자.
마지막에 합치자.</code></pre>

<p>이것이 SIMD의 감각입니다. SIMD는 마법이 아닙니다. <strong>반복되는 독립 계산을 한 번에 처리하는 방식</strong>이에요.</p>

<div class="callout callout-purple">
<p class="callout-title">여기까지가 핵심</p>
<p>1~3단계가 오늘의 뼈대입니다. C 코드를 쓰고, 어셈블리에서 벡터 레지스터를 찾고, CPU가 여러 개씩 처리한다는 감각을 잡았어요. 아래부터는 이 감각을 <em>더 깊이</em> 확인합니다.</p>
</div>

---



## 4단계 — 컴파일러가 못 풀 때



<p>컴파일러가 아무 루프나 SIMD로 바꾸지는 않습니다. 가장 중요한 조건은 <strong>독립성</strong>이에요.</p>

<p>아까 그 <code>dot</code> 함수를 다시 봅시다. 같은 코드를 두 가지 옵션으로 컴파일해보세요.</p>

<pre><code>clang -O3 -S dot.c -o dot_o3.s
clang -O3 -ffast-math -S dot.c -o dot_fast.s</code></pre>

<p>두 어셈블리를 비교해보면 차이가 보일 수 있어요. 왜냐하면 floating point 덧셈은 수학의 실수 덧셈과 완전히 같지 않기 때문입니다.</p>

<pre><code>(a + b) + c  ≠  a + (b + c)    (floating point에서)</code></pre>

<p>순서를 바꾸면 마지막 비트가 달라질 수 있습니다. 그래서 컴파일러는 조심해요. <code>-ffast-math</code>는 컴파일러에게 이렇게 말하는 것에 가깝습니다.</p>

<blockquote>
<p>floating point의 아주 엄격한 규칙보다 속도를 우선해도 됩니다.</p>
</blockquote>

<p>컴파일러가 SIMD를 만들 수 있으려면, 계산이 독립적이거나, 순서를 바꿔도 된다고 판단할 수 있어야 합니다.</p>



## 5단계 — 진짜로 의존성이 있는 코드



<p>이번에는 정말로 SIMD가 어려운 코드를 봅시다. 파일 이름은 <code>prefix.c</code>.</p>

<pre><code>#include &lt;stddef.h&gt;

void prefix_sum(
    const float *a,
    float *out,
    size_t n
) {
    if (n == 0) return;

    out[0] = a[0];

    for (size_t i = 1; i &lt; n; i++) {
        out[i] = out[i - 1] + a[i];
    }
}</code></pre>

<p>이 코드는 이전 결과가 필요합니다.</p>

<pre><code>out[1] = out[0] + a[1]
out[2] = out[1] + a[2]
out[3] = out[2] + a[3]</code></pre>

<p>앞사람이 끝나야 뒷사람이 시작해요. 줄이 생깁니다. <strong>SIMD는 줄을 싫어합니다.</strong></p>

<p>직접 확인해보세요.</p>

<pre><code>clang -O3 -ffast-math -S prefix.c -o prefix.s</code></pre>

<p>어셈블리에서 <code>v0.4s</code> 같은 벡터 레지스터가 <em>보이지 않을</em> 겁니다. 컴파일러도 이 루프는 쪼개지 못합니다.</p>

<div class="callout callout-amber">
<p class="callout-title">내적 vs prefix sum</p>
<p>내적은 쪼개기 쉽습니다. prefix sum은 쪼개기 어렵습니다. 이 차이를 느끼는 것이 중요해요. SIMD는 <em>나란히 놓인 독립 계산</em>을 좋아합니다. 줄을 세워야 하는 계산은 싫어합니다.</p>
</div>

---



## 6단계 — 벤치마크로 숫자 보기



<p>이제 숫자를 봅시다. 파일 이름은 <code>bench.c</code>.</p>

<pre><code>#include &lt;stddef.h&gt;
#include &lt;stdio.h&gt;
#include &lt;stdlib.h&gt;
#include &lt;time.h&gt;

#define N ((size_t)1024 * 1024 * 64)
#define R 200

float dot(
    const float *a,
    const float *b,
    size_t n
) {
    float sum = 0.0f;

    for (size_t i = 0; i &lt; n; i++) {
        sum += a[i] * b[i];
    }

    return sum;
}

static double now_sec(void) {
    struct timespec ts;
    clock_gettime(CLOCK_MONOTONIC, &amp;ts);
    return ts.tv_sec + ts.tv_nsec / 1000000000.0;
}

int main(void) {
    size_t bytes = N * sizeof(float);

    float *a = aligned_alloc(64, bytes);
    float *b = aligned_alloc(64, bytes);

    if (!a || !b) return 1;

    for (size_t i = 0; i &lt; N; i++) {
        a[i] = (float)(i % 100) / 100.0f;
        b[i] = (float)((i * 3) % 100) / 100.0f;
    }

    double start = now_sec();
    float result = 0.0f;

    for (int r = 0; r &lt; R; r++) {
        result += dot(a, b, N);
    }

    double end = now_sec();

    printf("result: %f\n", result);
    printf("time: %.3f sec\n", end - start);

    free(a);
    free(b);
    return 0;
}</code></pre>

<p>컴파일합니다.</p>

<pre><code>clang -O0 bench.c -o bench_o0
clang -O3 bench.c -o bench_o3
clang -O3 -ffast-math bench.c -o bench_fast</code></pre>

<p>실행합니다.</p>

<pre><code>./bench_o0
./bench_o3
./bench_fast</code></pre>

<p>결과는 환경마다 다릅니다. 하지만 대체로 이런 흐름을 기대해요.</p>

<pre><code>-O0        느림
-O3        빠름
-O3 fast   더 빠를 수 있음</code></pre>

<p>여기서 중요한 것은 정확한 초 단위가 아닙니다. 중요한 것은 질문이에요.</p>

<blockquote>
<p>왜 같은 C 코드인데 속도가 달라졌을까?</p>
</blockquote>

<p>답은 어셈블리에 있습니다. 컴파일러가 CPU에게 다른 명령을 줬기 때문이에요.</p>

---



## 7단계 — 정렬된 메모리



<p>벤치마크 코드에서 메모리를 이렇게 잡았어요.</p>

<pre><code>float *a = aligned_alloc(64, bytes);</code></pre>

<p><code>malloc</code>을 써도 됩니다. <code>malloc</code>도 연속된 메모리를 줘요. 차이는 <strong>시작 위치</strong>입니다.</p>

<p><code>aligned_alloc(64, bytes)</code>는 64-byte 경계에 맞춰 시작하는 메모리를 요청합니다. SIMD는 여러 원소를 한 번에 읽는데, 데이터가 경계에 잘 맞아 있으면 CPU가 읽기 좋아요.</p>

<p>정렬되지 않아도 현대 CPU는 대부분 처리합니다. SIMD가 안 되는 것은 아니에요. 하지만 경계에 걸친 load가 늘면 비용이 생길 수 있습니다.</p>

<div class="callout callout-teal">
<p class="callout-title">aligned_alloc의 의미</p>
<p>SIMD를 가능하게 만드는 것이 아닙니다. <em>SIMD가 더 편하게 먹을 수 있게 담아주는 것</em>이에요. SIMD의 주인공은 여전히 루프의 모양입니다. 하지만 실무에서는 데이터 배치와 정렬도 같이 봅니다.</p>
</div>



## 8단계 — 남은 찌꺼기 — tail loop



<p>SIMD는 묶음 단위로 처리합니다. float 4개씩 처리한다고 해보세요. <code>n = 10</code>이면?</p>

<pre><code>0 1 2 3    → SIMD
4 5 6 7    → SIMD
8 9        → ?</code></pre>

<p>앞의 8개는 SIMD로 처리하기 좋습니다. 남은 2개는 애매해요.</p>

<p>보통 컴파일러는 두 루프를 만듭니다. SIMD 루프와 tail 루프.</p>

<pre><code>// vector loop
for (; i + 4 &lt;= n; i += 4) { ... }

// tail loop (스칼라)
for (; i &lt; n; i++) { ... }</code></pre>

<p>큰 덩어리는 SIMD로 먹고, 남은 찌꺼기는 하나씩 먹습니다. 어셈블리에도 이 흔적이 남아요. vector loop가 있고, 그 뒤에 작은 scalar loop가 붙습니다.</p>

<p>그래서 SIMD가 항상 정확히 4배 빨라지는 것은 아닙니다. 루프 진입 비용도 있고, tail 처리도 있어요. 하지만 큰 배열에서는 tail은 거의 무시할 수 있습니다. 중요한 건 <em>큰 덩어리를 CPU가 한 번에 먹는다</em>는 점이에요.</p>

---



## 9단계 — Java에서도 된다



<p>이 이야기는 C만의 이야기가 아닙니다.</p>

<pre><code>static float dot(float[] a, float[] b) {
    float sum = 0.0f;

    for (int i = 0; i &lt; a.length; i++) {
        sum += a[i] * b[i];
    }

    return sum;
}</code></pre>

<p>최신 JVM은 이런 패턴을 인식할 수 있어요. JIT이 실행 중에 컴파일하면서 SIMD 명령어를 만들 수 있습니다. C처럼 어셈블리를 바로 볼 수는 없지만, <em>원리는 같아요.</em></p>

<p>OpenJDK Vector API를 쓰면 더 명시적으로 표현할 수도 있습니다. 하지만 오늘의 핵심은 API가 아닙니다. 언어가 아닙니다.</p>

<blockquote>
<p>CPU가 보기에 이 계산은 여러 개를 한 번에 처리해도 안전한가?</p>
</blockquote>

<p>그 질문이 먼저입니다. 언어는 그 다음이에요.</p>

---



## 10단계 — 오늘의 정리



<p>오늘 우리는 내적을 계산했습니다.</p>

<p>C 코드로는 이렇게 썼어요.</p>

<pre><code>sum += a[i] * b[i];</code></pre>

<p>하지만 CPU는 이렇게 처리할 수 있었습니다.</p>

<pre><code>여러 개를 곱한다.
여러 개를 더한다.
부분합을 만든다.
마지막에 합친다.</code></pre>

<p>어셈블리에는 벡터 레지스터가 등장했어요.</p>

<pre><code>v0.4s</code></pre>

<p>float 4개. 한 번에 처리. 이게 SIMD입니다.</p>

<p><code>aligned_alloc</code>은 정렬. SIMD를 켜는 스위치가 아니라, CPU가 데이터를 편하게 읽도록 도와주는 것. 남은 찌꺼기는 tail loop가 처리합니다. Java도 할 수 있어요. 다만 확인이 더 어렵습니다.</p>

<p>그리고 — SIMD가 항상 되는 것은 아닙니다. 의존성이 있는 루프(prefix sum)는 컴파일러도 쪼개지 못해요. 이 차이를 느끼는 것이 오늘의 핵심입니다.</p>



## 오늘의 한 입



<p>SIMD는 손으로 벡터 명령어를 쓰는 기술이 아닙니다. <strong>컴파일러가 벡터 명령어를 만들 수 있는 코드를 쓰는 감각</strong>이에요.</p>

<p>내가 하나씩 계산한다고 썼더라도, CPU는 여러 개씩 계산할 수 있습니다. 조건은 하나.</p>

<blockquote>
<p>데이터가 나란히 있고, 계산이 서로 독립적이어야 한다.</p>
</blockquote>

<p>CPU는 생각보다 놀고 있습니다. 좋은 루프는 그 CPU를 깨웁니다.</p>

## 보너스 — Spark Tungsten이 한 일



<p>여기서 Spark Tungsten 이야기가 자연스럽게 이어집니다.</p>

<p>Tungsten은 보통 off-heap memory, unsafe row, whole-stage code generation, cache-aware execution으로 기억돼요. 다 맞습니다. 하지만 오늘 본 관점으로 다시 보면 한 줄로 줄일 수 있어요.</p>

<blockquote>
<p>CPU가 좋아하는 모양으로 데이터를 다시 담았다.</p>
</blockquote>

<p>객체 그래프는 CPU가 싫어합니다.</p>

<pre><code>User → Profile → Address → City</code></pre>

<p>포인터를 따라가야 해요. 메모리가 흩어져 있습니다. 예측하기 어렵습니다.</p>

<p>반면 columnar 데이터는 다릅니다.</p>

<pre><code>age:   [23, 18, 31, 27, 45, 19, 52, 40]
score: [0.8, 0.3, 0.7, 0.1, 0.9, ...]</code></pre>

<p>나란히 있습니다. 연속적이에요. CPU가 크게 떠먹기 좋습니다. SIMD는 단지 명령어 이름이 아닙니다. <em>데이터를 어떻게 놓을 것인가</em>의 문제예요.</p>
